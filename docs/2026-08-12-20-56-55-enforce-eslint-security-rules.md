# Title: Plan — Enforce ESLint Security Rules Across Server and Client

- **Classification:** feature
- **Description:** Add security-focused ESLint plugins and rules to both workspace apps at `error` severity, then fix every violation they surface so `lint:check` passes clean.

---

## Approach Summary / Goal

The two apps have different threat surfaces, so they get different rule sets rather than one copy-pasted block. The **server** is Node/NestJS — it gets `eslint-plugin-security` (Node-oriented: child_process, non-literal fs/regexp/require, weak randomness, timing attacks) plus core `no-eval`-family rules. The **client** is React/Next.js — `eslint-plugin-security` is largely irrelevant and noisy there, so it instead gets `eslint-plugin-no-unsanitized` (DOM XSS sinks) plus React security rules already available through `eslint-config-next`, at zero new dependency cost.

Both apps land at `error` severity per the user's instruction, with one deliberate exception called out under Risks. Existing violations get fixed in the same session.

**Goal:** `pnpm server lint:check` and `pnpm client lint:check` both exit 0 with security rules active and blocking.

## Functional Requirements

1. `apps/server/eslint.config.mjs` registers `eslint-plugin-security` and `eslint-plugin-no-unsanitized`; all enabled rules at `error`.
2. `apps/client/eslint.config.mjs` registers `eslint-plugin-no-unsanitized` and enables React/core security rules at `error`.
3. New dev dependencies added via `pnpm` to the correct workspace package (`--filter`), never to the root.
4. Every violation surfaced by the new rules is fixed in source; no rule is disabled to hide a violation, and no blanket `eslint-disable` file headers are added.
5. Any unavoidable suppression uses a narrow line-level `// eslint-disable-next-line <rule> -- <justification>` with a written reason.
6. `pnpm server lint:check` and `pnpm client lint:check` both pass.
7. `pnpm server format:check` and `pnpm client format:check` still pass (Prettier is wired through ESLint in both configs).

## Non-Functional Requirements

- **No runtime behaviour change** beyond what a violation fix strictly requires. This is a lint-hardening task, not a hardening rewrite.
- Rule blocks match each file's existing style: grouped, commented sparsely, appended after the existing rule groups.
- Server rules must not fight `tseslint.configs.recommendedTypeChecked`, already active.
- Client rules must not duplicate what `nextVitals` / `nextTs` already enable.

### Known violation

`apps/server/src/feature/cache/cache.service.ts:93` compiles a **user-supplied query parameter** into a `RegExp` — `security/detect-non-literal-regexp` will flag it, and it is a genuine ReDoS vector (mitigated only by `NonProductionGuard` blocking the endpoint in production). Proposed fix: cap pattern length and reject patterns containing nested quantifiers before compiling, keeping the existing `BadRequestException` contract. This is the one place the lint work touches real behaviour, and it makes the endpoint safer rather than merely quiet.

## Risks & Assumptions

- **`security/detect-object-injection` is proposed as `off`, not `error`.** This deviates from the user's "error, blocking" answer, so it is flagged rather than done silently. The rule fires on _any_ bracket access with a non-literal key (`obj[key]`) and has a very high false-positive rate; in a TypeScript codebase the key types already constrain it. The plugin's own maintainers keep it out of practical configs.
- **Assumption:** the client gets no `eslint-plugin-security`. Its Node-oriented rules produce noise, not signal, in a React app.
- **Unknown violation count.** A grep of both apps found a clean surface — no `dangerouslySetInnerHTML`, no `innerHTML`, no `eval`, no `child_process`, no `target="_blank"`, and only the one `new RegExp`. But greps aren't the linter; the real count only appears once the rules run. If the count turns out large, the developer sub-agent reports back rather than mass-suppressing.
- **`no-unsanitized` flat-config compat** is confirmed by its peer range (`eslint: ^9 || ^10`); both apps run ESLint 9.
- **`security/detect-possible-timing-attacks`** may flag comparisons in `encryption.service.ts` / `hash.service.ts` — both already use `timingSafeEqual` / `bcrypt.compare` and are genuinely safe, so those would be justified line-level suppressions, not code changes.
- **No tests.** `PROJECT_OVERVIEW.md` sets Testing Workflow to `Skip-Testing`, and the client has no test runner at all. Verification is `lint:check` + `format:check`, so **no tester sub-agent is spawned**.
