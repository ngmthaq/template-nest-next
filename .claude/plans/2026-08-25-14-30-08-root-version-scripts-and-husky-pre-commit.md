# Title: Plan — Root version-bump scripts + husky pre-commit (lint-fix & patch bump)

- Classification: feature
- Description: Add `version:major|minor|patch` scripts to the root `package.json`, then install husky + lint-staged so a `pre-commit` hook auto-fixes staged files with ESLint and bumps the root patch version into the same commit.

---

## Approach Summary / Goal

- Add three scripts to the root `package.json` that delegate to `pnpm version <major|minor|patch> --no-git-tag-version`, so each one edits only the root `version` field (`0.0.1` -> `1.0.0` / `0.1.0` / `0.0.2`) without creating a commit or a git tag.
- Install `husky` and `lint-staged` as root dev dependencies, add the standard `"prepare": "husky"` script, and create `.husky/pre-commit`.
- The hook runs `lint-staged` first (ESLint `--fix` on staged files only, dispatched per workspace because each app owns its own `eslint.config.mjs`), then runs the patch bump and `git add package.json` so the version increment is part of the commit being created.
- `--no-git-tag-version` is what makes the hook safe: a tagging bump inside `pre-commit` would try to commit during a commit and fail.
- **Goal:** three manual version-bump scripts at the root, plus an automatic lint-fix + patch bump on every commit.

## Functional Requirements

- `pnpm version:major` bumps root `version` `0.0.1` -> `1.0.0`; `version:minor` -> `0.1.0`; `version:patch` -> `0.0.2`. No git commit, no git tag created by any of the three.
- Neither `apps/client/package.json` (`0.1.0`) nor `apps/server/package.json` (`0.0.1`) is modified by these scripts.
- `git commit` triggers `.husky/pre-commit`, which: (a) runs ESLint `--fix` on staged JS/TS files only and re-stages what it fixed, (b) bumps the root patch version, (c) stages the modified root `package.json`.
- A staged file with an auto-fixable lint error is committed already fixed; a staged file with a non-fixable ESLint error aborts the commit with a non-zero exit.
- The resulting commit contains the version bump — the working tree is clean afterwards.

## Non-Functional Requirements

- Hook cost stays proportional to the commit: `lint-staged` runs ESLint only on staged paths, never a full two-app sweep.
- No new dependency in `apps/client` or `apps/server` — husky and lint-staged live at the workspace root only.
- Configuration follows existing conventions: pnpm workspace filters (`--filter @template-nest-next/*`), Prettier formatting already enforced through `eslint-plugin-prettier`.
- The hook must be idempotent and must not recurse (it creates no commits of its own).

## Risks & Assumptions

- **Node version mismatch:** root `engines` requires `node >=24`, the active shell runs `v22.22.2`. There is no `.npmrc`, so pnpm's `engine-strict` defaults to off and this should only warn — but if the install hard-fails, the developer must report it rather than editing `engines` or forcing the install.
- **Pre-existing leftover state:** `.husky/_/` exists untracked and `git config core.hooksPath` is already `.husky/_`, from an earlier husky that is no longer in `pnpm-lock.yaml` or `node_modules`. `husky init` regenerates this cleanly; assumption is no manual git-config surgery is needed.
- **Every commit changes `package.json`.** This is exactly what was asked for, but worth naming: rebases, cherry-picks and long-lived branches will conflict on the `version` line fairly often, and version numbers will climb quickly (one patch per commit, not per release). `git commit --no-verify` skips the bump; note that `git commit --amend` does NOT — pre-commit runs on amends too, so each amend bumps the patch again.
- `husky init` writes a placeholder `.husky/pre-commit` containing `npm test`; it will be overwritten with the real content, not appended to.
- Assumes ESLint flat-config resolution works when invoked with `pnpm --filter <app> exec eslint --fix <absolute paths>` — the developer must prove this by actually running it, not assume it.
