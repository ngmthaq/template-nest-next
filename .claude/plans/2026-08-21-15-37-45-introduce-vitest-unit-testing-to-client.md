# Title: Plan — Introduce Vitest unit testing to `apps/client`

- Classification: `feature`
- Description: Stand up a Vitest + jsdom + Testing Library harness in `apps/client` and write 10 colocated `*.spec.{ts,tsx}` files covering every project-authored util, hook, and component.

---

## Approach Summary / Goal

- `apps/client` has **zero** test infrastructure. The work splits cleanly into a config foundation (developer) and the specs themselves (testers), with the config a hard prerequisite.
- **Vitest over Jest** because Storybook already runs `@storybook/nextjs-vite` on `vite@^7`: the `@/*` alias, `jsx: react-jsx`, `resolveJsonModule`, and ESM all work through the pipeline that's already installed, instead of being re-wired through `ts-jest` transforms and `moduleNameMapper`.
- **Conventions mirror `apps/server` exactly**: colocated `*.spec.*` beside the source, `describe('<UnitName>')`, behavioural `it(...)` sentences with **no "should" prefix**, literal `// Arrange` / `// Act` / `// Assert` comments in every test, `passWithNoTests: true`, coverage reported but never gated.
- Every spec is **hermetic** — no real network, no real clipboard, no real `next/headers`. All boundaries stubbed.
- **Goal**: `pnpm client test` runs 10 green suites, and a contributor adding `app/(shared)/_utils/foo.ts` writes `foo.spec.ts` beside it with zero config changes.

## Functional Requirements

- `pnpm client test` discovers and runs `*.spec.{ts,tsx}` anywhere under `apps/client/app/`, and nothing outside it.
- All 10 spec files pass with no network access and no dev server running.
- `pnpm client test:cov` emits a coverage report that excludes specs, stories, and vendored shadcn — and **never fails on a threshold**.
- `pnpm client lint:check` and `pnpm client format:check` pass on every new file, including the specs.
- `pnpm client build` and `pnpm client storybook` are unaffected — no spec file reaches the Next build output.
- `apps/client/.storybook/` is **not modified**; `parameters.a11y.test` stays `'todo'`.

## Non-Functional Requirements

- **Hermetic**: no real `fetch`, clipboard, cookie jar, or `next/headers`. `vi.stubGlobal` / `vi.mock` at every boundary.
- **AAA structure**: one Act per test, explicit `// Arrange` / `// Act` / `// Assert` comments, per the `aaa-testing` skill.
- **Fast**: whole suite well under 30s; all timer-dependent tests use `vi.useFakeTimers()` rather than real waits.
- **No production-code changes.** Not one file that ships is modified. If a unit proves untestable without a source change, that is a blocker to surface — not a licence to edit.
- **Test isolation**: `useScript`, `useStyle`, and `useWindowResize` hold **module-level registries/caches**. Specs must use `vi.resetModules()` or per-test-unique keys, and prove isolation by passing under `--sequence.shuffle`.

## Risks & Assumptions

- **Assumption**: `*.spec.*` colocation and the no-"should" `it(...)` sentence style are carried over from `apps/server` without asking, since that convention is already established repo-wide and documented in `docs/2026-08-20-11-18-11-colocate-server-unit-tests-with-source-files.md`.
- **Risk (medium) — ESLint has no file-glob overrides.** Specs face the full `jsx-a11y` strict set, `better-tailwindcss`, `no-unsanitized`, `simple-import-sort`, and Prettier-as-error. Unlike the server, `no-unsafe-*` type-checked rules are **not** active, so idiomatic `vi.fn()` mocking should pass. **If it does not**, the sub-agents must **not** edit `eslint.config.mjs` — they report the exact rule + file list as a blocker and the Root Agent brings it back to the user.
- **Risk (medium) — module-level shared state.** `useScript`/`useStyle` share a `registry` Map and `useWindowResize` a `cachedSize`. Without `vi.resetModules()` these leak across tests and produce order-dependent passes. Mitigated by an explicit shuffle-run acceptance criterion (task 15).
- **Risk (low) — `cookieUtils` server branch.** `scope()` keys off `typeof window !== 'undefined'`, but jsdom always defines `window`. Tests will use `vi.stubGlobal('window', undefined)` rather than a second Vitest environment, to keep one config.
- **Risk (low) — `cacheUtils` imports `next/cache` at module top level** (`cacheTag`, `refresh`, `updateTag` are canary APIs under `cacheComponents: true`). The whole module is `vi.mock`ed so the Next server runtime is never loaded; the pure `normalize`/`toTag`/`toTags` logic is unaffected.
- ~~**Assumption**: `cn` gets a thin spec (3–4 cases) despite being a one-line re-export of `clsx`+`twMerge`.~~ **Superseded 2026-08-24**: the user ruled `cn` needs no spec because it comes from a library; `cn.spec.ts` was written, then deleted. `cn.ts` itself is unchanged.
- **Confirmed**: no CI workflow exists (`.github/` absent) and `.husky/` has **no active hooks** (husky isn't even in the lockfile), so nothing will auto-run this suite. It is a manual `pnpm client test`.
- **Confirmed**: none of these utils/hooks has a single call site in the app — they are template library code. These specs will be the only thing exercising them, which raises their value but means no integration signal backs them up.
