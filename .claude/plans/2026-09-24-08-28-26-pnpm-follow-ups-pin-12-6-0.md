# Title: Plan — pnpm follow-ups: pin 12.6.0, keep the Docker cache, commit

- Classification: feature
- Description: Pin pnpm 12.6.0 (it fixes the lockfile bug), require it as the minimum, keep the Docker base layer cached, check everything, and commit.

---

## Approach Summary / Goal

- pnpm v12.6.0 (2026-09-22) fixes pnpm/pnpm#14926, the bug that kept changing `pnpm-lock.yaml`. We pin to it, set `engines.pnpm` to `>=12.6.0`, and regenerate the lockfile.
- The hook keeps `npm version`. The long bug note in CONTRIBUTING becomes one short line that gives the reason.
- Docker caching: a small first stage reads only the `packageManager` value out of `package.json` into a file. The base stage copies that file and runs `corepack prepare "<value>" --activate`. BuildKit caches a `COPY` by file content, and the version bump leaves this file unchanged, so the base layer stays cached. The version is still set in one place.
- Goal: pnpm 12.6.0 everywhere, a lockfile that no longer changes, the Docker base layer cached across commits, everything verified and committed.

## Functional Requirements

- Root `package.json` has `packageManager: "pnpm@12.6.0"` and `engines.pnpm: ">=12.6.0"`.
- `pnpm-lock.yaml` is regenerated with 12.6.0. Running `pnpm install --frozen-lockfile`, then `pnpm exec true`, then `pnpm --filter @template-nest-next/client exec true`, then `pnpm version patch --no-git-tag-version --no-git-checks` leaves it byte-for-byte the same.
- README, CONTRIBUTING, and PROJECT_OVERVIEW say pnpm `>= 12.6.0`. The CONTRIBUTING bug paragraph is replaced by one short line explaining why the hook uses `npm version`.
- Both Dockerfiles get the pnpm version only from root `package.json`, with no hardcoded version. When only `"version"` in `package.json` changes, the base stage (the `corepack prepare` step) shows as `CACHED` on rebuild.
- All CI commands, both full Docker builds (logs show pnpm v12.6.0), and a real commit through the hook pass, and the tree stays clean.

## Non-Functional Requirements

- `allowBuilds` stays the same. No new dependencies.
- Dockerfile changes stay small and match the current style.

## Files in Scope

- `package.json`, `pnpm-lock.yaml` (and `pnpm-workspace.yaml` only if pnpm 12.6.0 itself rewrites it)
- `README.md`, `CONTRIBUTING.md`, `.claude/references/PROJECT_OVERVIEW.md`
- `apps/server/Dockerfile`, `apps/client/Dockerfile`

## Risks & Assumptions

- Risk: npm tags 12.6.0 as `next-12`, not `latest`, so it may have bugs that are not known yet. The full CI, Docker, and hook checks lower this risk.
- Risk: if the lockfile still changes on 12.6.0, the developer stops and reports back. We do not add a workaround.
- Assumption: BuildKit caches `COPY --from=<stage>` by file content, so the base stage stays cached. The developer proves this with two builds.
- Assumption: the commit at the end includes all current uncommitted changes (the earlier round and this round) plus both plan files, and the hook runs as normal.

## Open Questions / Blockers

- Task 3 found that the server Docker build fails on pnpm 12.6.0 with `ERR_PNPM_RECURSIVE_RUN_NO_SCRIPT` at `pnpm --filter @template-nest-next/server deploy`. Root cause, proven with a small test workspace: in 12.6.0, a root script named `deploy` hides the built-in `pnpm deploy`. The user chose to rename the root script to `deploy:vm` (tasks 2b and 3c).
